# How real desktop apps separate UI from backend so the UI can be swapped

Research for the Evrakçı rebuild decision. Every claim has a source URL inline. Items I could not confirm from a primary source are marked **(unverified)**.

## 1. The three patterns seen in practice

### A. Headless core as a separate process, UI talks over a protocol

- **Neovim** is the clearest case. "Nvim has a client-server architecture: by default when you run `nvim`, this starts the builtin UI client, which starts a `nvim --embed` server (child) process that the UI client connects to" ([neovim.io/doc/user/tui](https://neovim.io/doc/user/tui/)). The built-in terminal UI was moved from a thread into its own process in 0.9 (PR merged Dec 2022), and the release notes warned this "could cause subtle behavior changes" ([news-0.9](https://neovim.io/doc/user/news-0.9.html), [PR #18375](https://github.com/neovim/neovim/pull/18375)). All UIs, built-in or third party (Neovide etc.), are clients of the same msgpack-RPC API, and several can attach to one server ([vim_diff](https://NeoVim.io/doc/user/vim_diff.html), [Neovide bridge source](https://docs.rs/crate/neovide/0.16.1/source/src/bridge/mod.rs)).
  - Key design ideas: the UI opts into capabilities (`ext_linegrid`, `ext_multigrid`, `ext_popupmenu`, `ext_cmdline`), each of which hands one piece of presentation to the UI; when several UIs attach, Nvim uses only the capabilities every UI supports. Redraws are sent as batched `redraw` notifications and the UI must only show state after a `flush` event, so it never shows half-applied state ([api-ui-events](https://neovim.io/doc/user/api-ui-events/)).
  - Versioning: `api_level`, `api_compatible`, `api_prerelease`; "Function signatures will NOT CHANGE after release", "Deprecated functions will not be removed until Nvim 2.0" ([api](https://neovim.io/doc/user/api/)).
- **Language Server Protocol**: built to solve the "every editor × every language" problem by moving language logic into a separate process that speaks JSON-RPC ([LSP overview](https://microsoft.github.io/language-server-protocol/overviews/lsp/overview/)). It has `$/cancelRequest` (a cancelled request "still needs to return... a response"), token-based `$/progress` with begin/report/end, and capability negotiation in `initialize` where a missing capability means "absence of the capability" ([LSP 3.17 spec](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)).
- **Jupyter**: kernels and frontends talk over five ZeroMQ channels (shell, IOPub broadcast, stdin, control, heartbeat). Control is a separate socket so interrupt/shutdown "aren't stuck behind long-running executions"; the kernel publishes `busy`/`idle` status around each request; the spec "is versioned independently of the packages that use it" (currently 5.x) ([messaging spec](https://jupyter-client.readthedocs.io/en/latest/messaging.html)).
- **Syncthing**: Go daemon, the web GUI is just JavaScript calling the same REST API other programs can use, authenticated by `X-API-Key`; the docs warn "The interface is subject to change" ([REST API](https://docs.syncthing.net/dev/rest.html)). Events come through "a simple long polling interface for exposing events from the core utility towards a GUI" with strictly increasing ids so a client can detect missed events ([Event API](https://docs.syncthing.net/dev/events.html)).
- **Transmission**: daemon plus GTK/Qt/web/remote clients over HTTP POST JSON. CSRF protection via `X-Transmission-Session-Id` (server returns 409 with the correct id). In 4.1.0 it moved to JSON-RPC 2.0 with a semver `rpc_version_semver`, deprecating the older integer version fields ([rpc-spec.md](https://raw.githubusercontent.com/transmission/transmission/main/docs/rpc-spec.md)).
- **qBittorrent**: native Qt GUI plus a WebUI API; the WebAPI version is separate from the app version (`/api/v2/app/webapiVersion`), with cookie auth and a Referer/Origin check, and `sync/maindata` sends only deltas since the last response id (`rid`), falling back to `full_update` ([WebUI API wiki](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-(qBittorrent-4.1))). Third parties built complete replacement UIs on this API, e.g. VueTorrent ([github.com/VueTorrent/VueTorrent](https://github.com/VueTorrent/VueTorrent)).
- **Docker Desktop (Windows)**: the app talks to a SYSTEM-privileged `com.docker.service` over the named pipe `//./pipe/dockerBackendV2`, restricted to the `docker-users` group ([permission requirements](https://docs.docker.com/desktop/setup/install/windows-permission-requirements/)); security researchers found the pipe is an HTTP REST API and found privilege-escalation bugs in it ([CyberArk](https://www.cyberark.com/resources/ransomware-protection/breaking-docker-named-pipes-systematically-docker-desktop-privilege-escalation-part-1)).
- **Paperless-ngx**: Django REST Framework API with an Angular SPA. The "ng" fork added the Angular frontend over a REST API while the Django admin kept running next to it; the API has been versioned since paperless-ng 1.3.0 ([paperless-ng README](https://cdn.jsdelivr.net/gh/jonaswinkler/paperless-ng@master/README.md), [setup docs](https://github.com/jonaswinkler/paperless-ng/blob/ng-1.1.3/docs/setup.rst), [API docs](https://docs.paperless-ngx.com/api)).
- **Tauri sidecar**: any executable (the docs mention PyInstaller-built Python API servers) bundled via `externalBin`, with a required target-triple suffix in the file name ([Tauri sidecar docs](https://v2.tauri.app/develop/sidecar/)).

### B. In-process core library, UI(s) link to it

- **OBS**: "The OBS Studio backend is powered by the library libobs", which provides "the main pipeline, the video/audio subsystems, and the general framework for all plugins"; the Qt front-end is a separate layer with its own Frontend API ([OBS backend design](https://docs.obsproject.com/backend-design)).
- **Wireshark**: GUI, core, `epan` ("the packet analyzing engine"), `wiretap` (file I/O) and `dumpcap` (the only privileged part) are separate blocks ([Wireshark dev guide](https://www.wireshark.org/docs/wsdg_html_chunked/ChWorksOverview.html)). That split is what made the GTK→Qt swap possible (section 3).
- **Blender**: since 2.5, "operators" act as controllers in an MVC design between UI and data, and the UI layout itself is written in Python on top of the RNA data API ([Blender operators docs](https://developer.blender.org/docs/features/interface/operators/), [2008 data API proposal](https://lists.blender.org/pipermail/bf-taskforce25/2008-October/000029.html), [bpy_ops commit 2009](https://lists.blender.org/pipermail/bf-blender-cvs/2009-July/020853.html)). The same operators are callable from scripts, buttons, menus and shortcuts.
- **Calibre**: one Python codebase with Qt GUI, CLI (`calibredb`) and a content server; heavy jobs run in worker processes; `calibredb --with-library <server URL>` lets the CLI go through a running server instead of the files ([content server manual](https://manual.calibre-ebook.com/server.html), [calibredb](https://manual.calibre-ebook.com/generated/en/calibredb.html)).

### C. Core as a CLI that GUIs shell out to

- **Git**: "plumbing" commands "were designed to be chained together UNIX-style or called from scripts" and are "building blocks for new tools" ([Pro Git](https://git-scm.com/book/en/v2/Git-Internals-Plumbing-and-Porcelain)). GitHub Desktop uses dugite, which runs "the same command line interface that core Git offers" ([dugite](https://github.com/desktop/dugite)). This works because Git operations are coarse, but it gives a poor channel for progress, cancel and structured errors.

## 2. What worked and what failed

### The strongest negative evidence: xi-editor
Raph Levien's retrospective on xi (Rust core, native frontends over JSON-RPC) is the best post-mortem on this exact question: "I now firmly believe that the process separation between front-end and core was not a good idea." Async "made everything more complicated, in some cases considerably so"; word wrap during window resize produced races and tearing; scrolling took "months of work" to fetch text across the boundary, which an in-process structure would have made simple; JSON serialization hurt code size and Swift performance; error handling and version mismatch between ends were hard to get right. He still considered a process split fine for plug-ins (like LSP) ([xi retrospective](https://raphlinus.github.io/xi/2020/06/27/xi-retrospective.html)).

The lesson: a process boundary is cheap for **coarse, job-like** operations (run OCR, export, completions) and expensive for **fine-grained interactive** state (scrolling, live layout, per-keystroke editing). Evrakçı's review screen (page thumbnails, box overlays, typing corrections) is on the expensive side.

### Chatty APIs and state sync
- LSP critique: many features are "essentially state sync" but each implements it differently; responses can be reordered; with no causal ordering a client cannot tell whether a result reflects the latest document; the spec is large (90 methods, 407 types) and often imprecise about presentation ([Michael Peyton Jones, "LSP: the good, the bad, the ugly"](https://www.michaelpj.com/blog/2024/09/03/lsp-good-bad-ugly.html)).
- Working fixes seen in the wild: batched notifications plus a "flush" commit point (Neovim, [api-ui-events](https://neovim.io/doc/user/api-ui-events/)); delta sync keyed by a response id with a full-resync fallback (qBittorrent `rid`, [wiki](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-(qBittorrent-4.1))); monotonic event ids so missed events are detectable (Syncthing, [events](https://docs.syncthing.net/dev/events.html)).

### Versioning the protocol
- Successful projects version the protocol separately from the app: Jupyter ([spec](https://jupyter-client.readthedocs.io/en/latest/messaging.html)), qBittorrent `webapiVersion` ([wiki](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-(qBittorrent-4.1))), Transmission semver RPC ([rpc-spec](https://raw.githubusercontent.com/transmission/transmission/main/docs/rpc-spec.md)), Neovim `api_level` with additive-only rules ([api](https://neovim.io/doc/user/api/)). LSP's strict backwards compatibility is praised but leaves old behaviour as permanent burden ([michaelpj](https://www.michaelpj.com/blog/2024/09/03/lsp-good-bad-ugly.html)).
- What happens without it: syncthing-gtk, a third-party GUI, broke after Syncthing API changes and "cannot be started anymore" since Syncthing v2 ([AUR](https://aur.archlinux.org/packages/syncthing-gtk), [Linux Mint review](https://community.linuxmint.com/software/view/syncthing-gtk)). For Evrakçı, where the owner controls both sides, the risk is smaller but real if the UI and backend ever ship separately.

### Long-running jobs, progress, cancel
Every protocol that survived has explicit job semantics: LSP progress tokens and cancel ([spec](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)); Jupyter busy/idle status and a separate control channel for interrupts, with `interrupt_mode: message` for kernels that cannot take OS signals ([spec](https://jupyter-client.readthedocs.io/en/latest/messaging.html)). Calibre runs heavy work in worker processes ([manual](https://manual.calibre-ebook.com/server.html)). The design rule is: jobs have ids, state lives in the backend, the UI subscribes to events and can disconnect and reconnect without losing the job.

### Large binary data (page images)
Jupyter supports raw binary buffers after the JSON frames, but "no official messages make use of these buffers" ([spec](https://jupyter-client.readthedocs.io/en/latest/messaging.html)). Web-style backends such as Paperless serve thumbnails and previews as separate URL resources rather than inside JSON ([Paperless API](https://docs.paperless-ngx.com/api)). xi shows the cost of fetching viewport content across a boundary ([xi](https://raphlinus.github.io/xi/2020/06/27/xi-retrospective.html)). For a local app, the cheap answer is to pass page ids or file paths to a render cache on disk, not image bytes.

### Packaging two processes on Windows
- Orphaned backends are a recurring bug: Tauri issue "Sidecar process is still alive when the main process exits" ([#1896](https://www.github.com/tauri-apps/tauri/pull/1896)), plus follow-ups ([#2464](https://www.github.com/tauri-apps/tauri/pull/2464), [#3605](https://www.github.com/tauri-apps/tauri/pull/3605)); a PyInstaller-launcher write-up shows "the launcher is not the process" ([blog](https://timetobuildbob.github.io/blog/the-launcher-is-not-the-process/)). The standard Windows fix is a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` ([Raymond Chen](https://devblogs.microsoft.com/oldnewthing/?p=2433), [Microsoft docs](https://msdn.microsoft.com/library/ms684161(v=VS.85).aspx)).
- Installer upgrade issue: Tauri NSIS installer did not replace a sidecar on reinstall ([#15134](https://github.com/tauri-apps/tauri/issues/15134)).
- Python `multiprocessing` uses `spawn` on Windows and frozen apps must call `freeze_support()` (tested with cx_Freeze) or get a `RuntimeError` ([Python docs](https://docs.python.org/3/library/multiprocessing.html)).
- Antivirus: frozen Python executables (PyInstaller, Nuitka) are often flagged by Defender as false positives, and fixes are submission to Microsoft or rebuilding ([pythonguis](https://www.pythonguis.com/faq/problems-with-antivirus-software-and-pyinstaller), [discuss.python.org](https://discuss.python.org/t/pyinstaller-false-positive/43171), [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/4078397/where-executables-created-by-pyinstaller-are-being)). Whether a second cx_Freeze executable that opens a socket raises detections further is **(unverified)**.

### Local ports: firewall and security
- Binding to `0.0.0.0` triggers the Windows firewall prompt; binding to `127.0.0.1` generally does not (Wine changed its tests for this reason) ([Wine patch](https://list.winehq.org/mailman3/hyperkitty/list/wine-gitlab@winehq.org/message/ZRTQET2VH7SQT56IIHEAZS23YXHOMXJQ)). No Microsoft document states the exact rule **(unverified as official behaviour)**. Note `localhost` may resolve to IPv6 first ([thelinuxcode](https://thelinuxcode.com/127001-vs-0000-what-they-mean-when-to-use-each-and-how-to-debug-binding-bugs/)).
- A localhost web server is an attack surface for every web page the user opens: Zoom's hidden server on port 19421 let any site force-join a call with the camera on (CVE-2019-13450), and Zoom removed it ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2019-13450), [Rapid7](https://www.rapid7.com/blog/post/2019/07/10/zoom-video-snooping-what-you-need-to-know/)). This is why Syncthing uses an API key, Transmission a session-id header, qBittorrent a Referer/Origin check, and Jupyter a token (access "means access to running arbitrary code", [Jupyter security](https://jupyter-server.readthedocs.io/en/latest/operators/security.html)). For KVKK data this matters: an unauthenticated local HTTP API would expose citizens' documents to any browser tab.
- stdio or a named pipe avoids ports entirely (LSP commonly uses stdio; Docker uses a named pipe with an ACL, [Docker docs](https://docs.docker.com/desktop/setup/install/windows-permission-requirements/)).

### Latency, startup, debugging
I found no rigorous benchmark of local JSON-RPC latency for Python backends; figures in blog posts (stdio ~1-20 ms, HTTP higher) are unsourced **(unverified)** ([dev.to](https://dev.to/corrupt952/how-i-simplified-my-macos-apps-ai-integration-by-adding-a-python-bridge-220o)). Debugging two processes is harder; Neovim's developer docs explicitly note that running the TUI involves two processes ([dev_tools](https://neovim.io/doc/user/dev_tools/)). Startup cost of a second frozen Python interpreter on Windows: **(unverified)**, measure it.

## 3. Undo, job state and validation belong in the backend

- **Undo**: the Command pattern is the standard. Each command knows how to apply and reverse itself, small commands can be merged, macros group several into one step, and a "clean" index tracks the saved state ([Qt Undo Framework](https://doc.qt.io/qt-6/qundo.html)). Qt's classes live in Qt modules, so a Qt-free core needs its own small pure-Python command stack with the same ideas. In Neovim the undo tree lives entirely in the server, so every GUI gets undo for free (follows from the client-server design in [tui](https://neovim.io/doc/user/tui/)). Blender ties undo to operators, so a button, a shortcut and a script all produce the same undo step ([operators](https://developer.blender.org/docs/features/interface/operators/)). Figma shows the subtle rules once undo crosses a client/server line: undo must modify redo history and vice versa, and "undo a lot, copy, redo to the present" must leave the document unchanged ([Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)).
- **Rule for Evrakçı**: every user change (correct a value, move a split, tick a box, re-run OCR on a page) becomes a named backend command with JSON-serialisable arguments. The backend owns the undo stack, the dirty flag and the history list. A UI only sends `execute(command)`, `undo()`, `redo()` and renders the resulting state. Then a new UI does not reimplement any of it.
- **Job state**: jobs are backend objects with ids, status, progress and cancel; the UI subscribes to events (Jupyter/LSP/Syncthing style, sources above). Jobs must survive a UI restart.
- **Validation**: rules (required fields, formats such as Turkish ID or tax numbers, cross-field checks) live in the backend and return structured problems (field, code, message key) that any UI can show. Capability flags, like Neovim's `ext_*`, let a simple UI ignore features it doesn't render.

## 4. Projects that actually swapped or added a UI

| Project | Change | How hard | Why it was possible |
|---|---|---|---|
| Wireshark | GTK → Qt, announced Oct 2013, Wireshark 2.0 Nov 2015; both UIs shipped side by side, legacy GTK removed in 2.2 | "rewriting thousands of lines of code", "a long and arduous process", about two years ([2013 blog](https://blog.wireshark.org/2013/10/switching-to-qt/), [LWN](https://lwn.net/Articles/667165/), [2.0 notes](https://www.wireshark.org/docs/relnotes/wireshark-2.0.0.html)) | Dissection engine (epan) and file I/O were already separate from the GUI ([dev guide](https://www.wireshark.org/docs/wsdg_html_chunked/ChWorksOverview.html)) |
| Neovim | TUI moved from in-process thread to a separate client process | One large refactor PR, with subtle behaviour changes ([PR #18375](https://github.com/neovim/neovim/pull/18375), [news](https://neovim.io/doc/user/news-0.9.html)) | The RPC UI protocol already existed for external GUIs |
| Jupyter | Classic Notebook → JupyterLab → Notebook 7 rebuilt on JupyterLab components | Multi-year; breaks classic extensions and customisations ([JEP 79](https://jupyter.org/enhancement-proposals/79-notebook-v7/notebook-v7.html), [migration guide](https://jupyter-notebook.readthedocs.io/en/v7.0.6/migrate_to_notebook7.html)) | Kernel protocol and server were unchanged; only the frontend moved |
| paperless → paperless-ng | Added Angular SPA over a REST API | Done as a fork because changes were "too big" for the main repo ([README](https://cdn.jsdelivr.net/gh/jonaswinkler/paperless-ng@master/README.md)) | Django backend reused |
| qBittorrent | Third-party full replacement WebUI (VueTorrent) | Done by outsiders with no core changes ([VueTorrent](https://github.com/VueTorrent/VueTorrent)) | Versioned, documented WebAPI |
| GIMP | GTK2 → GTK3 | Seven years for 3.0, touched "every aspect of the code for our user interface" ([GIMP 3.0 notes](https://gimp.org/release-notes/gimp-3.0.html), [announcement](https://gimp.org/news/2025/03/16/gimp-3-0-released)) | Counter-example: toolkit-to-toolkit within the same family still took years because UI code was large and intertwined (and the scope grew) |

Pattern: swaps went well where the core was already an engine with its own API (Wireshark, Jupyter, qBittorrent); they took longest where UI code itself was big and the port also became a redesign (GIMP). Even in the good cases, the UI rewrite was measured in years for a large UI. A 34k-line Qt widgets UI will not be "swapped by writing a connector"; the realistic promise of a clean boundary is that a new UI is *only* UI work, with no business logic to rediscover.

## 5. Recommendation for Evrakçı

**Boundary style: an in-process, protocol-shaped application API, with a JSON-RPC transport added only when a non-Python UI actually exists.**

1. Define one application layer in the Qt-free core: commands (with undo), queries, jobs and events, all taking and returning plain JSON-serialisable data (dataclasses/pydantic models with a published schema), plus a protocol version and capability list. Nothing passes Qt types or live Python objects across it. This is the Blender-operator / LSP-message shape without the process cost.
2. The Qt UI calls this API directly in the same process today through a thin adapter, with events delivered to the Qt thread. This avoids the xi trap for the interactive review screen ([xi](https://raphlinus.github.io/xi/2020/06/27/xi-retrospective.html)) and adds no second executable, port, AV or orphan-process problem.
3. Heavy work (OCR, OCRmyPDF, rendering) runs in worker processes owned by the core, like Calibre ([manual](https://manual.calibre-ebook.com/server.html)), with job ids, progress and cancel in the API.
4. Images cross the boundary as page ids or cache file paths, never as bytes in messages.
5. Keep the CLI as a second client of the same API from day one. A second client is the cheapest test that the boundary is real.
6. When a web or other UI is needed, wrap the same API in JSON-RPC 2.0 over stdio (child process) or a named pipe; if HTTP is unavoidable, bind to 127.0.0.1 only, with a random per-launch token and Origin checks ([Zoom CVE](https://nvd.nist.gov/vuln/detail/CVE-2019-13450), [Transmission](https://raw.githubusercontent.com/transmission/transmission/main/docs/rpc-spec.md)). Kill the child with a Windows Job Object ([Raymond Chen](https://devblogs.microsoft.com/oldnewthing/?p=2433)).

### The 3 biggest risks
1. **Logic leaking into the UI.** With AI agents writing most code, validation, undo and job bookkeeping will drift into Qt widgets unless enforced. Mitigation: an import-linter rule that the core cannot import Qt and the UI cannot import core internals (only the API module), and tests that drive every user action through the API without a UI.
2. **A chatty, fine-grained API that later cannot go over a process boundary.** If the in-process API returns live objects or needs dozens of calls per repaint, a later JSON-RPC transport will hit xi's problems. Mitigation: design calls as if they were remote (batch queries, event deltas with ids, a "flush"-like commit point, [Neovim](https://neovim.io/doc/user/api-ui-events/), [qBittorrent](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-(qBittorrent-4.1))), and run the test suite through a JSON round-trip serialiser to prove it.
3. **Expecting the boundary to make a UI swap cheap.** Every real swap above took one to several years for a large UI. The boundary removes the business-logic risk, not the UI effort. Budget accordingly, and if a split process is introduced later, budget for Windows packaging (second frozen executable, AV false positives, orphan processes, installer upgrades), which is a recurring source of bugs in the sources above.
