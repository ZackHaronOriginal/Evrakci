# 02: Tech stack for the Evrakçı rebuild (backend and UI)

Research date: 27 November 2026. I checked package licences against the live registries (crates.io API, NuGet registration API, PyPI JSON API) on that date. Anything marked **unverified** is my own estimate or comes from a single weak source.

## 1. Summary

- **Recommendation: keep Python for the core and make it a strict, typed, UI-free engine.** Put a versioned local API (JSON-RPC over stdio or localhost) between the engine and any UI. Keep PySide6 for now and replace the UI piece by piece. If the owner still wants .NET later, the step is a **.NET UI shell (WPF or Avalonia) driving the Python engine as a worker process**. A full C# or Rust rewrite is the wrong step.
- The deciding factor is the PDF/OCR toolchain. OCRmyPDF and pikepdf (both MPL-2.0) do text-layer grafting and PDF/A without Ghostscript, and neither .NET nor Rust has a permissive equivalent. In those stacks Evrakçı would have to rebuild that part itself.
- Licence traps appeared during the research. **PDFsharp 6.5.0 (October 2026) moved to AGPL-3.0-only.** The QuestPDF Community licence is not open source, and it excludes public-sector entities.
- The evidence that AI agents write better C# or Rust than Python is mixed. On realistic repository-level tasks, agents still resolve the most Python issues.

## 3. Licence findings that matter for an AGPL + CLA business

The owner sells commercial licences next to the AGPL edition. Every dependency therefore has to allow two things: being part of an AGPL release, and being part of a closed commercial build.

1. **PDFsharp changed licence.** The NuGet registry lists PDFsharp 6.2.4 (January 2026) as MIT, and both **6.5.0 and 7.0.0-preview-2 (14 October 2026) as `AGPL-3.0-only`** ([NuGet PDFsharp 6.5.0](https://www.nuget.org/packages/PDFsharp/6.5.0)). The fork io7.FreePDF says it "continues from the last MIT source" and describes 6.5/7.0 as "AGPL or a commercial licence" ([io7.FreePDF](https://www.nuget.org/packages/io7.FreePDF/)). The empira site still says MIT ([pdfsharp.net licensing](https://pdfsharp.net/Licensing.ashx)). I found no official announcement, so the motive is unverified. The practical rule: pin ≤6.2.4 or don't use PDFsharp. An AGPL dependency rules out selling closed licences unless empira's commercial licence is bought as well.
2. **QuestPDF is not open source.** Community License 3.0 (effective 6 July 2026) calls itself "source-available" and "not an OSI-approved open-source license". It is free under USD 1M revenue, but public-sector entities and listed companies are excluded ([QuestPDF Community License](https://www.questpdf.com/license/community.html), [pricing](https://questpdf.com/pricing.html)). A Turkish chamber of commerce is a public-law professional body, so it may count as "public sector". That is a legal question I could not settle (**unverified**). QuestPDF is also a poor fit inside an AGPL distribution. Avoid it.
3. **GPL-only Rust crate.** The `pdfium` crate (not `pdfium-render`) is GPL-3.0 ([docs.rs pdfium](https://docs.rs/crate/pdfium/0.10.3/source/Cargo.toml)). Use `pdfium-render`, which is MIT/Apache.
4. **Slint** (Rust GUI) is GPL-3.0 or the Slint Royalty-Free licence ([LibHunt comparison](https://www.libhunt.com/compare-iced-vs-slint)). The royalty-free terms would need checking before shipping a commercial build.
5. **PySide6** is LGPL-3.0 / GPL ([PyPI](https://pypi.org/project/PySide6/)). Qt's documentation warns commercial Qt customers against `pip install pyside6`, because the Community Edition is LGPL ([Qt for Python commercial use](https://doc.qt.io/qtforpython-6/commercial/index.html)). The LGPL itself is fine for both editions as long as Qt stays dynamically linked and replaceable, which is the case today.
6. **Nuitka** is now AGPL-3.0 with a runtime exception, so compiled binaries are not bound by it ([Nuitka on PyPI](https://pypi.org/project/Nuitka/), [Nuitka downloads](https://nuitka.net/doc/download.html)). It is safe to use as a build tool.

## 4. The hard part: what replaces OCRmyPDF?

OCRmyPDF renders a text-only layer with Tesseract and grafts it onto the original page, so the image is not recompressed ([OCRmyPDF advanced docs](https://ocrmypdf.readthedocs.io/en/stable/advanced.html)). Version 17 added `--pdfa-backend internal`, which makes PDF/A without Ghostscript and validates the result with pikepdf's PDF/A support ([v17 release notes](https://ocrmypdf.readthedocs.io/en/latest/releasenotes/version17.html)). This matters for Evrakçı because Ghostscript is AGPL and therefore off-limits.

Neither .NET nor Rust has an equivalent package. A port would have to rebuild:
- Tesseract's `textonly_pdf` output, overlaid page by page onto the source PDF. This technique is documented on the Tesseract mailing list ([tesseract-ocr group](https://groups.google.com/g/tesseract-ocr/c/ZufLmDe7qKA)). In .NET the overlay would use PdfPig or PDFsharp 6.2.x; in Rust, lopdf.
- PDF/A conversion: XMP metadata, OutputIntent/ICC profile, font embedding checks, and validation.

This is the most error-prone piece of the whole product, and OCRmyPDF has years of edge-case fixes in it ([GitHub releases](https://github.com/ocrmypdf/OCRmyPDF/releases)). Rebuilding it is the single biggest cost of leaving Python. It is also the strongest reason to keep Python at least as a worker.

## 5. Packaging, start-up, antivirus

- **Python.** Frozen apps (PyInstaller, and probably cx_Freeze) get flagged by antivirus because bundling an interpreter looks like malware packing, and unsigned binaries add to the suspicion ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/4078397/where-executables-created-by-pyinstaller-are-being), [discuss.python.org](https://discuss.python.org/t/pyinstaller-false-positive/43171)). The usual fixes are code signing and per-release false-positive submissions to Microsoft ([false-positive guide](https://github.com/hankhank10/false-positive-malware-reporting)). One developer reports Nuitka dropped detections to 1 of 60 engines ([DEV post](https://dev.to/weisshufer/from-pyinstaller-to-nuitka-convert-python-to-exe-without-false-positives-19jf)), but that is a single anecdote. I found nothing specific on cx_Freeze (**unverified**).
- **.NET.** A self-contained folder plus Inno Setup works the same way as today. Velopack (MIT, [NuGet](https://www.nuget.org/packages/Velopack)) adds delta auto-updates. **Native AOT is not supported for WPF**: trimming is disabled because "almost no WPF apps are runnable after trimming" ([Microsoft trimming docs](https://learn.microsoft.com/dotnet/core/deploying/trimming/incompatibilities)). A proof-of-concept fork reports ~136 ms AOT start against ~650–730 ms JIT ([wpfaot](https://github.com/lezzi/wpfaot)). Avalonia supports Native AOT ([Avalonia XPF docs](https://docs.avaloniaui.net/xpf/deployment/native-aot)). A JIT WPF start of under a second is fine for an office app.
- **Tauri.** It uses the system WebView2. On offline PCs either the ~127 MB offline installer or a fixed runtime of ~150–180 MB is needed, and a fixed runtime gets no Windows security patches ([Tauri Windows guide](https://v1.tauri.app/v1/guides/building/windows), [Microsoft WebView2 distribution](https://learn.microsoft.com/microsoft-edge/webview2/concepts/distribution)). Python can be bundled as a "sidecar"; the Tauri docs name PyInstaller-bundled Python as a common case ([Tauri sidecar](https://v2.tauri.app/develop/sidecar)). Known problems: killing the onefile launcher can leave the Python process orphaned ([blog](https://timetobuildbob.github.io/blog/the-launcher-is-not-the-process/)), and NSIS builds can ship a stale sidecar ([tauri#15134](https://github.com/tauri-apps/tauri/issues/15134)).
- **Support windows.** .NET 10 LTS runs to 14 November 2028, and .NET 8 left support on 10 November 2026 ([.NET support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)). The task brief's ".NET 8/9" is therefore already out of date: a .NET build has to target .NET 10 and move to the next LTS every two to three years.

## 6. Throughput on 1000+ page jobs and threading

- **PDFium is not thread-safe in any language.** pypdfium2 forbids concurrent PDFium calls "not even with different documents" and tells users to parallelise with processes ([pypdfium2 API docs](https://pypdfium2-team.github.io/pypdfium2/python_api.html)). A PDFium maintainer suggests running several PDFium processes ([pdfium group](https://groups.google.com/g/pdfium/c/HeZSsM_KEUk)). Rust code serialises pdfium-render behind a mutex for the same reason ([kreuzberg source](https://docs.rs/crate/kreuzberg/4.9.8/source/src/pdf/bindings.rs)). So the GIL is not what limits Evrakçı: rendering needs processes or a lock in C# and Rust too.
- **Tesseract also scales best as one process per page**, with `OMP_THREAD_LIMIT=1`, and OCRmyPDF manages this itself ([OCRmyPDF advanced docs](https://ocrmypdf.readthedocs.io/en/stable/advanced.html), [tesseract-ocr thread](https://groups.google.com/g/tesseract-ocr/c/Zo4jqQT0--w)).
- **The heavy work is native in every stack.** PDFium, Tesseract and ONNX Runtime do the work, and the host language only coordinates. .NET or Rust helps with the parts that are pure Python today: page bookkeeping, image glue in Pillow/numpy, and UI responsiveness. In a 1000-page job those parts are small next to OCR (**unverified**, needs profiling on Evrakçı's own pipeline).
- **Free-threaded Python** is officially supported in 3.14 but optional. PEP 779 allows up to ~15% slowdown and ~20% more memory, and C-extension support is still catching up ([PEP 779](https://peps.python.org/pep-0779/)). Evrakçı doesn't need it.
- **Memory.** Keep pages on disk and stream them, whatever the language. A 1000-page job held in RAM as bitmaps is a design bug in any language.

## 7. Migration stories

- **Calibre stayed on Python + Qt.** It is ~500k lines of Python, and Kovid Goyal ported all of it plus "tens-of-thousands of lines of extension code" to Python 3 for calibre 5.0 in 2020 ([9to5linux](https://9to5linux.com/?p=4799), [calibre 5.0 notes](https://calibre-ebook.com/new-in/fourteen)). Back in 2009 he described the approach: Python for 90–95% of the work, C for the hot spots ([PyQt list](https://riverbankcomputing.com/pipermail/pyqt/2009-February/022075.html)). This is the closest single-maintainer precedent to Evrakçı.
- **Anki: Python/Qt shell, Rust core.** Most backend logic is now in a Rust library (rslib). Python (pylib) wraps it through protobuf-defined RPCs, and the GUI mixes PyQt with TypeScript web views ([Anki architecture](https://docs.ankiweb.net/developers/architecture), [language bridge](https://docs.ankiweb.net/developers/language_bridge)). Anki shows that a hybrid can be reached gradually behind a stable API without a big-bang rewrite.
- **Dropbox rewrote its Python sync engine in Rust (Nucleus, 2020).** The main reasons were a data model that could not be fixed piece by piece and an engine that could not be tested reliably; the language was secondary ([Dropbox tech blog](https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine), [testing post](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)). It took a large team several years. Evrakçı does not have Dropbox's problem.
- **1Password 8** built a shared Rust core with an Electron UI. They describe it as "a Rust app with an Electron driven UI", and users complained about the non-native feel ([1Password blog](https://1password.com/blog/1password-8-the-story-so-far)). The core/UI split is the lesson worth copying.
- **Microsoft Teams** moved from Electron to WebView2 and claims up to 50% less memory and 2× faster launch. These are Microsoft's own benchmarks ([Microsoft Tech Community](https://techcommunity.microsoft.com/blog/microsoftteamsblog/microsoft-teams-advantages-of-the-new-architecture/3775704)).
- **Electron to Tauri.** Installers and idle memory shrink, but one team reports 22% more platform-specific bugs because each OS ships a different WebView. Most write-ups are low-quality blog posts ([Hopp benchmark](https://dev.to/gethopp/tauri-vs-electron-performance-bundle-size-and-the-real-trade-offs-1el4), [Better Stack](https://betterstack.com/community/guides/scaling-nodejs/tauri-vs-electron-vs-deno-vs-electrobun/)).
- **PyQt to C#/WPF.** I found no documented post-mortem, only forum threads ([r/csharp thread](https://pol1.lr.ggtyler.dev/r/csharp/comments/1kkqh89/migration_from_python_pyqt_to_c_wpf)). Treat any claimed cost or outcome for this path as **unverified**.

## 8. How well AI agents code in each stack

- **Repo-level issue fixing, which is closest to how Evrakçı is built.** On SWE-Sharp-Bench (Microsoft, 150 C# tasks), "70% of Python tasks in SWE-Bench Verified are solved, [but] only 40% of the C# tasks… under identical model-agent configurations". The authors partly blame larger C# patches ([arXiv 2511.02352](https://arxiv.org/html/2511.02352v1)). On Multi-SWE-bench, Rust resolve rates were ~2–8% against ~25–48% for Python with 2025 models ([arXiv 2504.02605](https://arxiv.org/html/2504.02605v1)). SWE-bench Multilingual points the other way: Rust had the *highest* rate, 58%, against 43% overall ([swebench.com/multilingual](https://www.swebench.com/multilingual)). So the Rust results conflict.
- **Self-contained problems.** On AutoCodeBench, C# scores far higher than Python or Rust: for Claude Opus 4, 74.9 for C# against 40.3 for Python and 38.7 for Rust ([arXiv 2508.09101](https://arxiv.org/html/2508.09101v1)). Generated C# for a well-specified function is good. The repo-level gap comes from navigating a codebase and making large edits.
- **Type checkers as feedback.** GitHub links TypeScript's rise to #1 to AI tools benefiting from types ([Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/)) and cites a study in which 94% of LLM compile errors were type-check failures ([GitHub blog](https://github.blog/ai-and-ml/github-copilot/why-ai-is-pushing-developers-toward-typed-languages/); the underlying study is **unverified**). Meta's Pyrefly team found that type-checker feedback raised agent success from ~80% to ~84%, but only in already well-typed Python ([Pyrefly blog](https://pyrefly.org/blog/type-checking-agentic-workflows/)). Agents also overuse escape hatches: they use `any` 9× more often than humans in TypeScript ([arXiv 2602.17955](https://arxiv.org/html/2602.17955)). Rust's compiler loop works for agents, with ~74% of real compile errors fixed automatically ([RustAssistant](https://www.microsoft.com/en-us/research/publication/rustassistant-using-llms-to-fix-compilation-errors-in-rust-code/)).
- **What this means for Evrakçı.** Python with strict pyright/mypy, no `Any` allowed, and a big test suite gets most of the typing benefit while staying in the language where agents score best on repo-level work. C# is a reasonable second choice. Rust has the least consistent evidence and the most friction for a single owner.

## 9. UI options

- **WPF** is mature and Windows-only. Microsoft still invests in it: .NET 9 added a Fluent/Windows 11 theme with light, dark and accent colours ([What's new in WPF .NET 9](https://learn.microsoft.com/dotnet/desktop/wpf/whats-new/net90)). Reviewers called that theme half-finished at launch ([Thurrott](https://www.thurrott.com/dev/312947/modernizing-netpad-net-9-arrives-with-a-few-small-improvements-for-wpf)).
- **WinUI 3** is Microsoft's newest native UI framework ([Windows developer FAQ](https://learn.microsoft.com/en-us/windows/apps/get-started/windows-developer-faq)), but it is Windows-only and would drop the Linux build. Its tooling and roadmap are widely questioned ([Avalonia comparison, vendor source](https://avaloniaui.net/winui-compare)).
- **Avalonia** (MIT) is the .NET choice that keeps Linux, and it supports AOT. The paid "Accelerate" tier covers only the new tooling ([Avalonia blog](https://avaloniaui.net/blog/building-a-sustainable-future-for-avalonia)).
- **Web UI (Tauri, or WebView2 inside a .NET shell)** gives the most UI freedom and an easy route to a later office-network mode, with a browser client against the same API. The costs are WebView2 distribution on offline PCs and a third language (TypeScript).
- **PySide6 (current)** works, and 34k lines of it already exist and are tested. The only change needed is to keep it as a thin client of the engine API.

## 10. Recommendation for Evrakçı

**Phase 1 (now, low risk): split the code, keep the language.**
1. Turn the Qt-free core (~5k lines) into an **engine process** with a versioned JSON-RPC (or local HTTP) API: job submit, progress events, page queries, corrections, export. Type it strictly (pyright `strict`, no `Any`) and build contract tests on the API schema. The schema becomes the long-term asset, because any future UI (WPF, Avalonia, web or a network client) talks to it.
2. Move the PySide6 UI onto that API, one tab at a time. It never imports the core directly.
3. Run rendering and OCR in a **process pool** inside the engine, as PDFium and Tesseract require, with page images on disk. This handles thousands of pages, and the same engine can later serve other office PCs.
4. Fix the Windows trust problem directly with Authenticode signing. Try Nuitka if cx_Freeze builds get flagged.

**Phase 2 (only if a concrete pain shows up): replace the shell, not the engine.** If the PySide6 UI becomes the bottleneck (look, accessibility, hiring, agent output quality), build a **.NET 10 WPF UI** (Windows-first) or an **Avalonia UI** (to keep Linux) against the same API. The Python engine stays as a worker, with OCRmyPDF, pikepdf and rapidocr unchanged. New C# features can also use ClosedXML, MiniExcel or Open XML SDK in the shell, all permissive. This is the Anki/1Password pattern: shared core, swappable UI.

**Not recommended: a full C# or Rust rewrite.** The main reasons:
- OCRmyPDF-grade text layering and Ghostscript-free PDF/A would have to be rebuilt from scratch.
- The licence ground is moving: PDFsharp went AGPL, QuestPDF is source-available.
- The GIL isn't the real constraint, since PDFium forces processes anyway.
- Agent benchmarks favour Python for repository-level work.
- A full rewrite of ~39k lines by a single owner, plus re-testing with office staff, is months of work with no new feature for users.

**Rough cost (my estimates, unverified, agent-assisted, one owner):**
- Phase 1 engine API and UI decoupling: 3–6 weeks.
- Phase 2 new .NET UI over the API, reaching parity with the 34k-line PySide6 UI: 3–5 months.
- Full C# port including an OCRmyPDF replacement: 6–9 months or more, mostly spent on PDF/A and text-layer edge cases.
- Rust + Tauri: longer still, with a third language for the UI.

**What to keep in every scenario:** the Python engine as the OCR/PDF worker (OCRmyPDF, pikepdf, pypdfium2, rapidocr, zxing-cpp), the template and test corpus, the job file format, and Inno Setup for installs. The Python dependencies are all permissive or MPL, which keeps the AGPL + CLA dual-licence model intact. If a .NET shell is added, pin any PDFsharp to ≤6.2.4 and keep QuestPDF out.
